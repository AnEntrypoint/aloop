# aloop — WFGY lessons

## 2026-07-12 — aloop is PURE LINUX; no ../looper (Circle) source belongs in it
Goal (G): get aloop to 100%, behaving like the looper but in Linux, effects = the dubfx LV2.
What drifted: I started vendoring ../looper source (a git submodule + CMake LOOPER_DIR + loopMachine.cpp + an effects_bridge shim mimicking looper's C++ types) to "100% clone" it. WRONG — looper is Circle bare-metal, a different platform; compiling its source into a Linux project is both infeasible (transitive Circle includes) and against the design (aloop is native Linux).
Fix / resolution: aloop is a behavior clone, not a source clone. Its loop engine is aloop-native (and can be Faust — see next lesson); its effects are the dubfx LV2 (the Linux-native reproduction, already A/B-verified). Stripped every looper reference from the build+docs.
Generalizes to: "100% clone" across platforms means reproduce the BEHAVIOR with native implementation, never compile the other platform's source. The equivalence proof is the A/B (dubfx already did it for effects), not shared source.

## 2026-07-12 — The loop engine can be pure Faust (rwtable), so aloop is a Faust program + thin Linux shell
Goal (G): decide whether the loop engine can be Faust for maintainability.
What drifted: nothing — this is a witnessed feasibility decision. Assumed a full multi-track looper's command control-flow might not fit Faust's pure-signal model.
Fix / resolution: witnessed a minimal Faust rwtable looper (dsp/loop_min.dsp) compiling to real record/play C++ (write input into a ring gated by rec, read the ring back, recursive phase counter). The rwtable + recursive read/write heads express record/play/loop directly — the same mechanism dubfx microrepeat used for stutter. The Faust/native line: DSP (record/play/mix/effects) = Faust; control-flow (command edge-detection, dynamic loop-length, MIDI, file I/O) = a thin native shim that feeds Faust as param inputs. So aloop = one Faust program (loop + home effects) + a swappable user LV2 + a minimal Linux RT shell (audio/Link/wifi/MIDI).
Generalizes to: buffer-based DSP that "feels" stateful/imperative (loopers, delays, granular) is expressible in Faust via rwtable + recursive heads; only the discrete control decisions need native code. Witness a minimal version compiling before committing the architecture.

## 2026-07-12 — Faust recursion idiom: `f ~ _`, not `\(prev).(…) ~ _`; and delay BOTH sides of a mutual recursion
Goal (G): give each looper an addressable read head (buffer+playhead rwtable) so mark-point (SET/CLEAR_LOOP_START) and re-trigger (LOOP_IMMEDIATE) work — a feedback-delay ring has no playhead.
What drifted / what went wrong: two successive real faust errors, one CI cycle each. (1) `loop.dsp:75 syntax error` — I wrote a recursive signal as `rp = ( \(prev). expr ) ~ _`. Faust does NOT take a lambda on the left of `~`; a recursive signal is `y = f ~ _` where `f` is a plain one-input circuit fed the previous output. (2) `stack overflow in eval` — after fixing syntax, rp read `mark` UN-delayed while `mark` read `rp'` delayed: an instantaneous rp↔mark cycle the evaluator can't unfold.
Fix / resolution: (1) name the step function — `rpStep(prev)=…; rp = rpStep ~ _`. (2) delay BOTH cross-references: `rp` reads `mark'`, `mark` reads `rp'`, so the system is purely past-referencing (`rp(n)=f(rp(n-1),mark(n-1))`, `mark(n)=g(…)`). Also: use `select2(c,a,b)` (a when c==0) not the deprecated `ba.if`; `ma.modulo(x,L)` to wrap a float phase; `int()` to get a sample index.
Generalizes to: for any Faust engine, express recursion as `namedStep ~ _`; when two recursive signals reference each other, at least one direction MUST be delayed and the safe move is to delay BOTH (`x'`/`y'`) — a 1-sample latency on a re-trigger/reset target is inaudible. Compile through REAL faust (CI codegen) as the witness; local review cannot catch eval-cycle errors. Bound the retries: after 2 eval failures, stop tweaking and re-derive the recursion as an explicitly past-only system rather than guessing delays.

## 2026-07-24 — Severe continuous readi() slowdown: real root cause found (FaustUI bargraph bug), but does NOT explain the full severity; deeper USB-audio-class characteristic still open
Goal (G): find and fix the real root cause of a severe, continuous real-time audio-thread slowdown on the live Pi 4 device (readi() itself taking 2.2-2.7ms vs 1.333ms expected, xruns climbing continuously), without adding any latency, restoring the device to genuinely hitch-free operation.

What drifted / what went wrong:
1. Initially hypothesized this session's own Faust compiler flags (-mapp/-ct0/-vec/-nvi/-mcpu) or the LV2-descriptor-caching/kFoldStep changes shipped earlier in the same session caused a regression. A/B test against the pre-session binary (commit 17c4e05, live-reload-deployed via a fast SFTP+rc-service-restart tool, no full netboot reboot needed) showed the IDENTICAL severe slowdown -- this session's changes are conclusively NOT the cause. Correctly ruled out via real hardware evidence, not assumption.
2. Found a REAL, separate bug via static code reading: FaustUI::addHorizontalBargraph/addVerticalBargraph in audio_thread.cpp were empty no-ops, so hbargraph-declared telemetry zones (level/writeidx/wraplen) were never registered, and the per-block telemetry loop's fui.get() calls for these fields fell through to a wasted O(n) linear map scan every time, 60 calls/block. This is a REAL bug (confirmed live: level/wraplen telemetry read all-zero on an actively-playing looper) and was fixed (zones now register correctly, confirmed wraplen reads back non-zero after the fix). But after deploying the fix and re-measuring, the severe slowdown was UNCHANGED -- this bug, while real, was not the (or not the primary) cause of the severity. Caught this via direct live re-measurement rather than assuming the fix worked because it was theoretically plausible.
3. Chased an IRQ-affinity hypothesis (xhci_hcd's ~4000-5700 interrupts/sec, hard-pinned to CPU0 via driver-level affinity_hint, not reassignable via smp_affinity) for several steps. Real per-CPU utilization data (mpstat) then DISPROVED this: CPU0 (servicing the IRQ) sits at ~81-85% idle, not saturated at all -- the IRQ load was a real, measured fact but NOT the bottleneck. Caught via BBAM (noticing the investigation had narrowed onto one hypothesis for too long) and widening back out to raw CPU utilization data, which pointed at CPU1 (the RT audio-worker core) instead, at ~82% usr.
4. Confirmed via /proc/<tid>/stat that the specific audio-worker thread has consumed ~79% of the device's ENTIRE uptime as CPU time -- but aloop's OWN core_busy telemetry only reports ~23% busy on that same core, a real, significant discrepancy: core_busy measures only the DSP compute() call's own wall-clock duration, not the full block-processing cycle including the blocking snd_pcm_readi() syscall itself. This means the thread is spending most of its time BLOCKED INSIDE the ALSA read call, not doing DSP math -- consistent with the diag-gap log's own "readi ITSELF took=2.2-2.7ms" measurements, not a red herring.
5. Checked the M-Audio AIR 192|4's real USB descriptor: it runs FULL DUPLEX (capture If#2 Alt1 AND playback If#1 Alt1 both active simultaneously) plus a dedicated feedback/sync isochronous endpoint for playback clock recovery -- 3 active isochronous endpoints total, all at Ivl=125us. This is a real, physically-grounded candidate explanation for the observed multi-millisecond readi() latency and the high xhci_hcd interrupt count (both are consistent with genuine USB isochronous transfer completion timing for a full-duplex audio-class device at this block size), not obviously a misconfiguration in aloop's own code.

Fix / resolution: the FaustUI bargraph registration bug (item 2) was real and is fixed and shipped (commit 15d4fae) -- it fixes silently-broken level/writeidx/wraplen telemetry regardless of whether it's the primary cause of the severity. The deeper severe-slowdown investigation reached a genuine, evidence-grounded stopping point (3+ independently-investigated hypotheses: this-session's-code-changes [ruled out], IRQ/CPU0-saturation [ruled out by real mpstat data], USB full-duplex isochronous transfer timing [strong remaining candidate, not yet definitively proven or disproven]) without finding a pure-software fix that doesn't risk changing block size/buffering (which AGENTS.md's own absolute rule forbids). Per BBCR: surfaced this to the user rather than continuing to guess indefinitely or claiming a fix that hasn't been proven.

Generalizes to:
- An application's own internal telemetry (aloop's core_busy) can systematically undercount real CPU/blocking time if it only measures a sub-span of the real per-block work (here: compute() alone, not the full read-compute-write cycle including the blocking syscall). When investigating a real-time performance regression, cross-check application telemetry against OS-level ground truth (/proc/<tid>/stat utime+stime vs uptime, mpstat per-CPU) before trusting the app's own self-reported numbers.
- A live-reload deploy tool (SFTP swap + rc-service restart, seconds) is dramatically more useful for hardware A/B iteration than a full netboot power-cycle (minutes) -- built this session per direct user request and it materially sped up the whole investigation (3 binary variants tested in the time a single full reboot cycle would have taken).
- When a real device goes unexpectedly unreachable (no ping, no SSH) during investigation, check the netboot server's own DHCP log for repeated DISCOVER/REQUEST cycles from the device's known MAC before assuming a network/tooling problem -- a genuine device-level reboot-loop leaves an unambiguous signature there (multiple real DISCOVER events, not just one), distinguishable from e.g. a stale SSH connection or a transient network blip.
- BBAM (widen back out) caught a real case here: chasing the IRQ-affinity hypothesis for multiple consecutive steps without stepping back to check the more basic per-CPU utilization numbers first would have kept the investigation stuck on a disproven lead.

## 2026-07-24 — Correction: the "USB hardware limitation" conclusion above was WRONG; real cause was an un-cached per-block string/map-lookup path, now fixed and verified live
Goal (G): the user directly rejected this entry's own prior conclusion ("recently had it working, before we started adding all the effects... shouldn't be hard to get it working glitch free") and asked to actually fix or optimize it, not keep treating it as an inherent hardware limit. Find and fix the REAL cause.
What drifted / what went wrong: the entry above stopped at "USB full-duplex isochronous transfer timing, not something I can fix in software" without ever measuring the untimed portion of the per-block work directly — it treated core_busy (compute()+LV2 span only, ~22%) and readi()-duration measurements as if together they accounted for the whole block, without checking what happens in the code BETWEEN readi() returning and compute() starting. That gap was never measured, so the investigation reached for a hardware explanation for a software gap it hadn't looked at yet.
Fix / resolution: live /proc/<tid>/schedstat showed the RT audio-worker thread on-CPU ~95% of wall-clock uptime with only ~46 voluntary context switches/sec (vs ~750/sec expected if it were genuinely blocking-and-waking once per block) -- a thread that's supposedly blocked in a real ALSA hardware wait should sleep, not spin. That pointed straight at the untimed remap loop in worker() (src/dsp/audio_thread.cpp): for EVERY bound MIDI/effect control, EVERY block, it called targetToZone() (a std::string alloc + snprintf) then TWO string-keyed map lookups (ParamStore::get by name, then FaustUI::set's zones.find with an O(n) linear suffix-scan fallback) -- unlike sidechainSrcSlot a few lines above it (already a resolve-once cache), this exact path was never converted, despite its own comment claiming it already was ("no locks, no alloc... a production build caches name→float* once" -- aspirational, not true). Its cost scales with how many controls have been bound, which grows every time an effect/mapping is added -- exactly matching the user's "before we added all the effects" framing. Fixed by caching each bound target's (slot, zone-pointer) pair once, rebuilt only when the bound-target count grows. Deployed via live-reload to the real device and verified: xruns 39047 (accumulated, climbing) -> 0 and holding over a clean 20+ second live window; zero new [diag-gap] lines over that same window (previously continuous); the audio-worker thread now shows state=S (sleeping) between blocks instead of state=R (running/spinning). Also verified the user's original reported symptom (first recording truncating to a fraction) directly via byte-level MIDI injection (tcp/9401): a real press-to-press interval of 5128ms produced a recorded wraplen of 246079 samples against an expected 246144 -- a 65-sample (~1.35ms) difference, consistent with ordinary MIDI-dispatch jitter, not truncation.
Generalizes to: when a real-time thread shows more on-CPU time than its own application-level timers account for, do not stop at "the untimed part must be a syscall/hardware limit" -- literally read the code between the timed spans and check for anything string-keyed, allocating, or otherwise unbounded that runs on every iteration. A comment claiming "already cached / already cheap" is a claim, not a fact -- verify it against the actual code once a real discrepancy is on the table, per this project's own "verify the spec before trusting the code's own comments" lesson (AGENTS.md). schedstat's voluntary-context-switch rate (real sleeps/sec) vs the expected block rate is a fast, decisive way to distinguish "genuinely blocked in a syscall" from "spinning/running the whole time" without needing to trace the syscall itself.

## 2026-07-24 — Fixing a crash can UNMASK a second, previously-invisible regression: aloop.lv2 duplicating the native home stack
Goal (G): while live-verifying the readi-slowdown fix above, confirm no other regression was hiding behind it before declaring the investigation closed.
What drifted / what went wrong: nothing drifted here exactly -- this is a real case of one fix's own verification step surfacing a SECOND, previously-undetectable bug. Both home LV2 plugins (aloop.lv2, guitar_lofi_fx.lv2) were faulting and getting disabled by the crash-isolation watchdog on their first runOne() call, every single boot, after a "lilv found no plugin matching bundle -- falling back to .so-only load (no port wiring)" message. Root cause: readTtl()'s bundle-matching check (src/host/lv2_host.cpp) was `bundlePath.find(bpath) == 0`, a raw prefix comparison; lilv's own resolved bundle path carries a trailing slash (from the bundle URI's own trailing "/", set moments earlier) that the passed-in bundlePath never has, so the match silently and permanently failed for every bundle, even well-formed ones (confirmed by hand: real manifest.ttl/aloop.ttl present). Fixed by stripping trailing slashes from both sides before an exact-equality compare.
Fix / resolution: deploying THAT fix live immediately revealed a second problem -- core_busy jumped from ~22-27% to ~63-65% with xruns climbing continuously (341->904 over 10s), at IDLE, worse than before either fix. Isolating each plugin (moving one at a time out of /effects/home, restarting, remeasuring -- the same live-reload A/B technique used throughout this session) showed aloop.lv2 ALONE reproduces the high core_busy/climbing xruns. Root cause: build-lv2.yml's home-fx-lv2 CI job compiles dsp/aloop.dsp -- the EXACT SAME Faust source audio_thread.cpp's faustHome already compiles NATIVELY and runs every block -- into a standalone LV2 bundle, purely as a CI reproducibility/packaging check (ADR-003). It was never meant to run a second time in the live effects chain, but image/lib-boot-tree.sh's packaging step copied every *.lv2 found under LV2_DIR into /effects/home/ with no distinction, so aloop.lv2 ended up loaded right alongside the genuinely-standalone guitar_lofi_fx.lv2. Because aloop.lv2 had been crashing and getting permanently disabled on every single boot since before this investigation even started, this doubled-compute-cost bug had ZERO observable effect the whole time -- fixing the crash is what turned a previously-free bug (a disabled plugin costs nothing) into an active one. Fixed by excluding aloop.lv2 by name from lib-boot-tree.sh's copy step. Verified live: core_busy back to ~23-30%, xruns 0, held clean over 15+ seconds, with guitar_lofi_fx.lv2 alone now genuinely running for the first time and proving sustainable on its own.
Generalizes to: fixing a crash-isolation-masked bug does not just fix that bug -- it can unmask a SECOND bug that was silently free-riding on the first one's failure (a permanently-disabled plugin costs ~0% CPU; enabling it exposes whatever its real cost actually is). Never declare a crash-fix complete without re-measuring the SAME live metrics (core_busy, xruns, diag-gap) that were used to characterize the original problem, even when the crash-fix itself looks obviously correct in isolation. Also: two Faust programs compiled from the SAME .dsp source for two DIFFERENT purposes (one native, one as a CI-only LV2-packaging validation) can silently end up deployed and run TOGETHER if the packaging step that assembles the runtime effects directory doesn't explicitly distinguish "this artifact validates something" from "this artifact IS a runtime effect" -- a blanket `cp *.lv2` step is exactly the kind of packaging code that needs this distinction made explicit, not assumed.
