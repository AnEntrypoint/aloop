Decision log (ADRs)

An append-only record of every non-obvious decision, with the rationale and the witnessed evidence behind it — so insight is never lost as the build progresses. New decisions append to the bottom. Each entry:

## ADR-NNN — <title>   (<date>, <phase/context>)
Decision: <what was decided>
Why: <the reasoning>
Evidence: <the witnessed fact — a file:line, a measurement, a doc reference>
Alternatives rejected: <what else was considered and why not>
Revisit if: <the condition that would reopen this>

The first block of ADRs is seeded from the feasibility study (FEASIBILITY.md); everything after is decided during the build.

ADR-001 — Target Alpine Linux + PREEMPT_RT on Raspberry Pi 4

Decision: Migrate the bare-metal Circle looper to Alpine Linux with a PREEMPT_RT kernel, on Pi 4. Why: Linux gives a filesystem + dynamic linker (needed for hot-swappable LV2 effects) and a tested WiFi/USB stack; PREEMPT_RT keeps worst-case scheduling jitter in the tens of microseconds so 64-sample blocks survive; Alpine’s diskless/RAM appliance mode gives near-bare-metal determinism. Evidence: FEASIBILITY.md — the whole study; the four goals are impossible on bare metal (no filesystem/linker) but feasible on Pi 4 Linux. Alternatives rejected: staying bare-metal (blocks hot-swap + carries the hand-rolled-driver maintenance); a full desktop distro (more background jitter than Alpine). Revisit if: the project moves to Pi 5 (see ADR-006).

ADR-002 — Effects are LV2 plugins hosted IN-PROCESS, never a JACK/PipeWire graph

Decision: dlopen the LV2 bundles and call run() inside aloop’s own audio callback; do not use a graph host. Why: A graph host schedules clients across period boundaries, adding one full audio period (~1.333 ms) of latency per hop — violating the no-added-latency goal. In-process calling adds zero latency. Evidence: witnessed latency arithmetic (FEASIBILITY.md, Requirement 3): serial-in-process = 0 ms added; fork-join parallel = 0 ms; JACK graph = +1 period. Combined chain ~0.9 ms fits one 1.333 ms block. Alternatives rejected: JACK2/PipeWire multi-client graph (adds a period); LV2 as just a static-linked struct with no swap (loses the moddability point). Revisit if: the chain becomes CPU-bound beyond what fork-join across Core 1+3 can cover.

ADR-003 — Reuse the dubfx verified Faust chain as the home-FX LV2

Decision: Package the dubfx Faust chain (pitch/delay/reverb/microrepeat/filters) with faust2lv2 as the fixed home effects bundle; do not re-derive the effects. Why: dubfx already reproduced looper’s effects and A/B-verified them sample-for-sample against the real C++. That work is done and witnessed; reusing it is correct and saves rebuilding. Evidence: dubfx README.md (10-preset A/B matrix, all pass); faust2lv2 codegen witnessed producing a 69 KB LV2 architecture with LV2_Descriptor refs. Alternatives rejected: rewriting the effects natively (wasteful; loses the A/B guarantee). Revisit if: never — this is a strict reuse.

ADR-004 — Live pitch = EngineSoladSnac (soladSnac), no signalsmith/RubberBand runtime dep

Decision: The live pitch stage links EngineSoladSnac (soladSnacOctaver.h + grainFormant.h) exactly as dubfx did via ffunction. Why: looper’s live pitch path uses ONLY EngineSoladSnac; the signalsmith/yinPsola/sincFormant engines are dead code removed from the wrapper. Matching looper means using soladSnac. Evidence: ../looper/patches/RubberBandWrapper.h:10-17 — “ONLY EngineSoladSnac is in the live pitch path. The former embedded signalsmith / yinPsola / sincFormant engines were dead members.” Alternatives rejected: using signalsmith/RubberBand (not what looper ships; would change the sound). Revisit if: looper’s live pitch engine changes.

ADR-005 — Ableton Link via the official library, over UDP

Decision: Delete the hand-rolled raw-Ethernet Link clone; use github.com/Ableton/link over ordinary UDP multicast 224.76.78.75:20808. Why: The bare-metal clone existed only because there was no IP stack. Linux has one, so the maintained library is correct, RT-safe, and interoperable. It maps onto the same lock-free snapshot handoff the looper already used. Evidence: FEASIBILITY.md R1; looper’s clone (abletonLink.cpp, 938 lines) is pure overhead on Linux; Ableton Link’s captureAudioSessionState is RT-safe. Alternatives rejected: porting the raw clone (maintenance burden, no benefit). Revisit if: never (the library is the standard).

ADR-006 — Pi 4 only; Pi 5 reopens the no-glitch guarantee

Decision: Target Pi 4. Treat Pi 5 as out of the current guarantee. Why: The no-glitch guarantee depends on steering WiFi/network IRQs off the audio core. Pi 4 allows this; Pi 5’s RP1 I/O controller has PF_NO_SETAFFINITY on force-threaded IRQ handlers, so those IRQs cannot always be moved. Evidence: FEASIBILITY.md Pi-4-vs-Pi-5 caveat; raspberrypi/linux#7301. Alternatives rejected: targeting Pi 5 now (risks R1’s no-glitch claim without a mitigation). Revisit if: the project must run on Pi 5 — then investigate RP1 IRQ handling / a mitigation before promising no-glitch.

ADR-007 — WiFi = autoAP mode-switching (STA-or-AP), not simultaneous AP+STA

Decision: Try station mode; host an AP only when no known network is available; switch back when one returns. Why: The requirement is “AP when external unavailable” = mode-switching, a solved pattern. Simultaneous single-radio AP+STA is flaky on the Pi (nl80211: Could not configure driver mode). Evidence: FEASIBILITY.md R4; looper already implements join-first-then-fallback-to-AP (kernel.cpp:85-169); the autoAP project. Alternatives rejected: simultaneous AP+STA on one radio (flaky). If ever truly needed → USB WiFi dongle for a second radio (documented, not built). Revisit if: a use case genuinely needs the Pi on home WiFi AND hosting a Link AP at the same time.

ADR-008 — USB audio via kernel f_uac2 configfs gadget

Decision: Replace looper’s hand-rolled UAC2 gadget (dwusbgadget.cpp) with the Linux f_uac2 configfs gadget on dwc2. Why: The kernel lays out isochronous USB packets correctly by construction, deleting the entire class of microframe-corruption bugs looper had to fix by hand. It is the hardest port but removes the most maintenance. Evidence: FEASIBILITY.md USB section; looper’s buzz/crackle history all traced to the hand-rolled decode. Alternatives rejected: porting the hand-rolled gadget (carries the bugs forward). Revisit if: f_uac2 cannot hit the latency target on-hardware (then measure and tune, don’t revert).

ADR-009 — Hardware-dependent verification is honestly marked, never faked

Decision: Rows that need a real Pi 4 to measure (RT jitter via cyclictest, f_uac2 round-trip latency, on-air Link no-glitch, AP multicast) are marked blockedBy: [external, no-Pi4-in-session] with the exact on-hardware test documented — never resolved as done from a dev host. Why: A measurement claim without the measurement is false completion. The build (code/config/CI/docs) is fully reachable now; only on-device numbers are external. Evidence: gm false-completion rule; these rows cannot be witnessed without hardware. Alternatives rejected: asserting the numbers from analysis (dishonest). Revisit if: a Pi 4 becomes available in-session — then run the documented tests and resolve with real output.

ADR-010 — Loop engine is a Faust rwtable ring with independent read/write heads (TRUE varispeed); mark-point playhead remains rejected

Decision (superseded from the original de.fdelay design, see history below): each of the 20 loopers is now a rwtable-based ring (dsp/loop.dsp’s oneLooper) with a monotonic WRITE index (reset at ARM, counts up freely during recording, bounded by MAXLEN) and a genuinely INDEPENDENT fractional READ accumulator (readPos ~ _, advancing by effSpeed samples-per-sample, linearly interpolated between two rwtable reads) — this is what makes real tape-style pitch+duration varispeed possible (the manual half/double-speed buttons and Ableton Link tempo tracking both drive effSpeed). wrapLen (the loop-length modulus shared by both read and write) latches from the write index’s own value at the FINISH edge (recording stop), not from any externally-supplied length at ARM — this avoids a cross-thread race with the native shell’s post-hoc length computation. A SEPARATE buffer+playhead design with an ADDRESSABLE read head (for the hardware’s mark-point commands, not for varispeed) was attempted and rejected — see Evidence. Why: The original de.fdelay delay-ring design could only vary LOOP LENGTH (which changed duration but not pitch) — it had no independent read/write heads, so it could not do real varispeed. The rwtable redesign (this session) replaces it specifically to enable genuine pitch-changing playback, matching ../looper’s actual m_playPos/m_playRate mechanism. The READ side only ever READS the table (two arbitrary-index lookups, floor/ceil for interpolation) and never writes back near where it read — this is NOT the same read-modify-write class that blocked the earlier addressable-mark-point playhead attempt (which needed to read a value and write the SAME read-back value into the SAME cell, to let a loop survive un-rewritten while not recording). Evidence: rwtable-based TRUE varispeed compiled clean via CI (Faust -lang cpp codegen, e.g. run 29451659654) and is deployed + live-verified on hardware this session (status.json: xruns:0, eff_speed present and tracking manual/Link speed). Two real Faust compile failures were hit and fixed DURING this redesign, both genuine mutual-recursion issues (not the RMW class): endless evaluation cycle of 19 steps when wrapLen’s finish-latch and writeIdx’s idle branch referenced each other circularly — fixed by making writeIdx’s idle state simply hold its last value instead of wrapping modulo wrapLen (commit 913ed1e). The EARLIER, separate mark-point-playhead attempt still failed for the ORIGINAL reason: 4 witnessed CI faust-codegen failures (loop.dsp:75 syntax error, stack overflow in eval rp↔mark mutual recursion twice, endless evaluation cycle of 8 steps on the write-back RMW) — see .wfgy/lessons.md (2026-07-12 Faust-recursion lesson). Consequence: mark-point / immediate-retrigger (0x08–0x0A) is STILL the one loop command family not reproduced — a deliberate, documented model difference (COMMAND-SURFACE.md), not a silent drop, and this remains true even after the rwtable migration (the migration was for varispeed, not for mark-point). Every other command maps 1:1, including TRUE varispeed (pitch+duration change together) which the old delay-ring design could never provide. Alternatives rejected: (a) an ADDRESSABLE preserve-on-hold mark-point playhead — still infeasible in pure Faust (the genuine RMW cycle, distinct from this ADR’s own rwtable varispeed reads); (b) implementing the loop buffer in native C++ instead of Faust — reintroduces hand-written DSP maintenance, defeating the single-Faust-program design (ADR-001) and the user’s standing directive to keep all DSP in Faust; (c) claiming mark-point works — false completion. Revisit if: a future Faust release supports a write-enable / RMW-safe table primitive, OR the mark-point behavior becomes a hard requirement (then the loop buffer moves to native C++ as a scoped, deliberate exception with its own ADR).

ADR-011 — Ship the flashable image with the stock Alpine kernel; PREEMPT_RT is an on-hardware optimization

Decision: The aloop-pi4.img ships Alpine’s stock linux-rpi kernel (from the Alpine RPi tarball) plus the full userspace RT tuning (isolcpus/nohz_full/rcu_nocbs/threadirqs in cmdline.txt + SCHED_FIFO + pinned affinity + mlockall). Building a PREEMPT_RT kernel (kernel/build-rt-kernel.sh) is an OPTIONAL step taken only if on-hardware measurement shows the stock kernel misses the 64-sample no-xrun target. Why: The user’s goal is to test from a card. A bootable image with the stock kernel + full userspace tuning boots and is testable TODAY, and running it is precisely how we measure whether the stock kernel already suffices. Gating card-testing on a ~30-min CI cross-compile of an RT kernel — which itself can’t be validated without the hardware we’re trying to reach — inverts the honest order. Ship + measure first, optimize second. Evidence: kernel/build-rt-kernel.sh writes the RT config fragment (PREEMPT_RT, NO_HZ_FULL, f_uac2/dwc2, HZ_1000) but does not build a kernel; the stock kernel ships in the tarball the image builder extracts; RT-TUNING.md documents the userspace knobs that apply regardless of kernel. Consequence: first-boot latency is whatever the stock kernel + tuning delivers — measured by test/hardware/test-rt-jitter.sh (shipped on the device). If it misses, build the RT kernel and re-flash; the fragment + cross-build recipe are ready. Alternatives rejected: (a) block the flashable image on a full RT-kernel CI build (inverts ship-then-measure; unverifiable without hardware); (b) claim RT latency without measuring (false completion, ADR-009). Revisit if: on-hardware RT-jitter measurement misses the target → run the RT-kernel build and fold it into the image.

ADR-013 — The Faust home DSP struct is heap-allocated in the audio worker thread, never stack-local

Decision: worker() (src/dsp/audio_thread.cpp) allocates AloopLoopDsp via std::make_unique<AloopLoopDsp>() at thread startup, binding a reference alias for the rest of the function. It is never declared as a plain stack-local (AloopLoopDsp faustHome;). Why: sizeof(AloopLoopDsp) is 336,326,896 bytes (~320 MiB) — the 20 loopers’ MAXLEN = 48000*60 (60s) delay-line buffers dominate. As a stack-local inside a pthread’s entry function, no thread stack size is large enough to hold it; a real, reproducible SIGSEGV was witnessed on a real Pi 4 at setRealtimeSelf’s very first prologue instruction. The heap allocation happens once at thread startup, never in the per-block RT hot path, so it carries none of the “no allocation in the audio callback” real-time risk the rest of this file is written to avoid. Evidence: gdb (debug build, -g -O0, unstripped, built via a temporary CI job) against a real core dump: print sizeof(AloopLoopDsp) → 336326896. Two prior hypotheses were tested and disproven first via live core-dump analysis: an explicit 8 MiB pthread stack (still crashed, identical offset) and a memlock/ulimit -l fix (crashed identically even with ulimit -l unlimited applied interactively). Fix verified live: rc-status shows aloop [started] (not crashed) staying up, /var/log/aloop.log shows a full clean startup, and a live UDP telemetry query returns real engine state. Consequence: any future Faust-generated struct added to the home stack must be checked for size before being declared as a local; if it is more than a few KB, heap-allocate it the same way. Revisit if: the loopers’ buffer sizing changes enough that stack allocation becomes plausible again (it will not — 20 loopers × 60s × 48kHz float buffers is inherent to the design, not incidental).

ADR-014 — ALSA PCMs are opened with explicit hw_params/sw_params against a stable device name, never “default” + convenience latency API

Decision: audio_thread.cpp opens its wire audio devices by stable name (never ALSA’s "default" PCM). hw_params are set explicitly (period_size = block_size exactly on the instrument device) instead of via snd_pcm_set_params()’s convenience latency argument. sw_params explicitly sets start_threshold to one period on both capture and playback. The f_uac2 gadget’s own req_number (isochronous USB request queue depth) is raised from the kernel default of 2 to 4 in src/usb/f_uac2-gadget.sh. Why: "default" is ambiguous without a shipped /etc/asound.conf (this device has multiple real ALSA cards — an instrument audio interface, a MIDI controller, and the OTG gadget — plus dmix/dsnoop’s own large fixed period on top), and snd_pcm_set_params(..., latency_us) picks whatever period/buffer satisfies a requested LATENCY NUMBER, not the configured block_size — the as-shipped code requested 20ms, ~15x the intended 1.33ms. Separately, the hw_params-default start_threshold for a from-scratch-configured playback stream is the full buffer size, but a loop that only writes one period per snd_pcm_writei() call before blocking on the next capture read never crosses that default threshold, so the stream stays permanently PREPARED (never actually running) while capture (whose default threshold is 1 frame) runs fine — the two streams silently desync. Evidence: all fixes were witnessed live on a real Pi 4 via SSH — /proc/asound/.../hw_params showing period_size:64 (matching block_size) after the device+hw_params fix (was an unpinned ~20ms request before); /proc/asound/.../status showing state: PREPARED (stuck) for playback before the sw_params fix, RUNNING after; /sys/kernel/config/usb_gadget/aloop/functions/uac2.0/req_number reading 4 after the gadget-script fix (was kernel default 2). A live diagnostic build (temporary fprintf logging on snd_pcm_readi/writei error codes, since removed) confirmed a residual xrun source was -EIO with a frozen hw_ptr on the gadget’s PCM specifically — traced to no host application actively streaming audio through the gadget device at verification time (confirmed with the user directly), i.e. expected idle-USB-audio-class behavior, not a code defect. This diagnosis was BEFORE ADR-015 corrected which physical device is actually the primary DSP I/O — see ADR-015 for why the gadget was never the right primary target to begin with. Consequence: any future change to block_size in aloop.conf automatically re-derives the ALSA period without further tuning (the hw_params call always targets N = block_size frames exactly). If a different or newer UAC2-class device is ever substituted, re-verify req_number and the sw_params thresholds against it — these are values tuned against THIS gadget driver’s specific behavior, not universal constants. Revisit if: a future USB audio gadget driver changes its own internal buffering defaults, or block_size is lowered enough that the gadget mirror’s buffering stops being sufficient against real-world USB scheduling jitter (re-measure xruns with an actual host audio session running, not an idle default-device check).

ADR-015 — Two distinct ALSA devices: the real instrument USB audio interface (primary, tight-latency) and the OTG gadget (mirror, best-effort)

Decision: audio_thread.cpp opens TWO separate ALSA devices, matching ../looper’s architecture exactly: instrumentDevice (aloop.conf [audio] instrument_device=, default hw:0,0 — the real USB audio interface an instrument/mic plugs into, e.g. the M-Audio AIR 192|4) is the primary capture+playback path the Faust engine reads from and writes to every block, blocking, tight-latency (matching block_size exactly, ADR-014). audioDevice (aloop.conf [audio] audio_device=, default hw:UAC2Gadget,0 — the f_uac2 OTG gadget) is opened SND_PCM_NONBLOCK and written to as a best-effort MIRROR of the same processed output after the instrument-device write, with a looser period/buffer (4x block_size) and silent absorption of -EAGAIN/errors — it can never stall, desync, or degrade the instrument device’s real-time path. Why: an earlier version of this code (before this ADR) opened ONLY the OTG gadget as the sole audio device — meaning the real instrument USB audio interface was NEVER read from or written to at all, and the user’s reported “no audible sound” / “no passthrough from input to output” was because the actual instrument input was never being captured. Deep research into ../looper’s reference implementation (patches/input_usb.cpp, output_usb.cpp, output_otg.cpp) confirmed the real architecture: AudioInputUSB/AudioOutputUSB (the USB-HOST audio class driver talking to the real external interface) are the graph’s ONLY real AudioConnection input/output nodes; AudioOutputOTG/AudioInputOTG are NOT audio-graph nodes at all — they are passive tap/inject shims that read/write the SAME ring buffers via independent cursors with deliberately looser latency targets (looper: OTG_LAG_TARGET=384 samples vs the real device path’s OUT_RD_TARGET=96, a 4x headroom difference), because OTG’s job is only to mirror audio to/from whatever host computer is on the cable, not to be the real-time-critical path. Evidence: /proc/asound/card0/stream0 (the AIR 192 4) showed Status: Stop on both playback and capture before this fix, confirming it was never opened. ../looper source citations: input_usb.cpp:206 (AudioInputUSB::inHandler, the real capture path), output_usb.cpp:188 (AudioOutputUSB::outHandler, the real playback path), output_otg.cpp:6-16 + output_usb.cpp:63 (AudioOutputUSB_tapOTG, the passive OTG mirror reading the same ring with an independent, longer-lag cursor), audio.cpp:147-148 (only input/output — the real USB-audio-interface objects — get AudioConnections in the graph; the OTG objects do not). Consequence: aloop.conf’s instrument_device= must be pinned correctly for the physical hardware in use (default hw:0,0 assumes the instrument interface enumerates before the gadget, true when the gadget is UAC2Gadget and not a numbered hw:N). If the instrument interface fails to open, audio stays down entirely (matching the pre-fix retry/backoff behavior) since it is now the primary path — the gadget mirror failing to open is silent-degrade-only and never blocks startup. Revisit if: a setup exists with no instrument USB audio interface at all (headless/OTG-only operation) — then instrument_device= would need an explicit “none” mode that falls back to the gadget as primary, which does not exist yet because no such deployment has been described.

ADR-012 — Sampler (chromatic + drum-record) ported as a bounded native C++ module, not folded into the Faust home stack

Decision: looper’s sampler subsystem (patches/sampler.h: note 65 held records ONE shared chromatic sample played back pitched per keybed key; note 66 held arms drum-record-mode, each keybed key recording into its OWN independent one-shot slot) IS reproduced in aloop, per explicit user request superseding this ADR’s original “not ported” decision. sampler.h was already written as a bare-metal-independent, portable C++ class (no Circle/loopMachine/masterPhase dependency) — ported near-verbatim to src/dsp/sampler/sampler.h, renamed Sampler/namespaced aloop, otherwise byte-for-byte identical algorithms/constants. Why: aloop’s home stack is ONE shared Faust program (ADR-001’s single-compile design) built around the 20-looper engine (loop.dsp), each looper being one feedback-delay ring bound to a fixed control group (looper%2i/rec etc, generated once via par at compile time). Drum-record-mode needs a DIFFERENT, independently-addressable per-key sample store (25 keybed keys, each its own record/play slot, unrelated to the 20 loopers) — a second, structurally distinct engine. Folding it into Faust (a second par-generated bank of 25 one-shot rings) would be a state-machine misfit (arm-then-record-one-shot vs the loopers’ continuous record/play) forced through a compile-time-fixed abstraction that doesn’t naturally express it. The originally-rejected alternative (b) — native C++ sample storage — is instead the RIGHT fit: Sampler is a genuinely separate, small, self-contained module (like the LV2 host, ADR’s own suggested “revisit” path), not a violation of ADR-001 (which is about the DSP effects/loop signal path staying one Faust compile, not a blanket ban on any native C++ subsystem existing alongside it). Evidence/implementation: Sampler is heap-allocated in worker() (audio_thread.cpp, same reasoning as AloopLoopDsp’s heap move, ADR-013 — its ~5.3MB of internal buffers are worth keeping off the thread stack) and published via a module-level g_sampler pointer, exposed through AudioThread::sampler() so the MIDI/control thread can push events (ApcGrid’s new onSamplerBtn65Press/Release, onSamplerBtn66Press/Release, onKeybedNoteOn/Off methods, src/control/apc_grid.h/.cpp) via the SAME lock-free SPSC event ring sampler.h already implements — no new cross-thread primitive needed. Per sampler.h’s own load-bearing invariant, captureBlock/renderInto run in worker() on the DRY input snapshot (fin[]) BEFORE the loop engine/effects chain (faustHome.compute), so sampler audio is recordable by a loop (under SHIFT fold) and receives the full effects chain exactly as looper’s renderInto-before-the-chain ordering requires. Consequence: config/controls.conf’s previously-unbound note-65/66/keybed range is now live. Every APC Key25 gesture from docs/COMMAND-SURFACE.md now maps 1:1 to looper except mark-point restart / loop-immediate (ADR-010, a genuine Faust-model limitation unrelated to the sampler). Alternatives considered: (a) reusing oneLooper for one-shot sample slots — rejected, wrong state machine; (c) leaving it undocumented/unimplemented — rejected per explicit user direction that no reachable scope stays undone. Revisit if: sampler audio needs to interact with microrepeat/varispeed in ways sampler.h’s independence-from-the-loop-engine design doesn’t anticipate — not expected given looper’s own design keeps them decoupled too.

ADR-016 — Resonode engagement crossfades the WHOLE dry/pitch-lock term against the resonator output, never sums into dry upstream

Decision: effects_runtime.dsp gates Resonode via a checkbox("fx/resonode/engaged")-driven smoothed resonodeEngageGate that crossfades (pitchStage(dry)*dryGate + dryWet) against resonodeOut immediately before the shared microStage:filterStage:delayStage:reverbStage tail, rather than summing resonodeOut into dry upstream of that machinery and letting the existing dry-passthrough gates (keyed only to the multitranspose voices) decide what’s audible. Why: the original implementation summed the resonator’s output into dry and ran the combined signal through the unchanged pitch-lock dry-passthrough gate, which is driven only by multitranspose voice gates — the resonator engaging never touched it, so raw dry (and harmonize’s own separate dry-passthrough term) stayed fully unmuted the entire time it was held. Audible result: the button engages the resonator, but the ordinary pass-through signal is still there too — exactly the failure mode ADR-004-adjacent “locked pitch must replace, never layer over, the original” rule already named for the transpose engine, just never extended to this instrument when it was added. Evidence: verified via the DawDreamer JIT harness (pitch.dsp stubbed to a bare passthrough): engaged + a held voice decorrelates the output from the raw dry input (r≈0.07 vs r≈0.997 disengaged) while producing real excited-resonator amplitude; engaged with no voice held decays to near-silence within one si.smoo time constant of the engage edge. At RESONODE_ENGAGED=0 the new formula is bit-for-bit the pre-fix formula (the resonator’s output is silent there anyway, since voices are never gated unless the instrument is engaged), so the disengaged path has zero behavioral change. Alternatives rejected: keeping the sum-into-dry topology and adding the resonator’s own gate as a second independent multiplier alongside the multitranspose gate — rejected per the same reasoning ADR-004’s sibling rule (loop-side “one gate, never two independently-paced ones”) already established: two independently-smoothed gates racing during a transition produces a real audible hump, not a clean crossfade. Revisit if: a future voice engine needs to coexist with both the resonator and multitranspose active simultaneously in a way this single shared crossfade point can’t express — not currently needed, the two are mutually exclusive via the bank-select mechanism.

ADR-017 — Granulator knob slots are 6 named-patch blend weights (convex combination), never 6 raw grain parameters

Decision: ApcGrid::applyGranulatorMorph treats each of the 6 LofiFx-bank knob slots as the blend weight of one of 6 fixed named grain patches (Glass/Cloud/Freeze/Chop/Tape/Shatter — each a full point in grain-size/density/pitch-spray/position-jitter/scan-rate/reverse-probability/envelope-shape space), normalizes the weights to sum to 1, and pushes the single resulting blended point into Sampler::setGrainPatch via one atomic call. Why: an earlier design mapped the 6 knobs 1:1 onto 6 independent raw grain parameters. Turning multiple knobs to their extremes simultaneously produced an incoherent, un-musical result — the parameters fight each other with no relationship to a real texture. Named patches give every knob position a musically-intentional destination; blending is a convex combination so any point in the 6-simplex is a coherent midpoint texture, and all-max is still a bounded, sane blend rather than the sum of six maxed-out raw parameters. Evidence: the previous per-setter design (six independent raw setters) let a caller apply a partial/inconsistent blend mid-update; the new design recomputes derived state exactly once per morph via the single atomic setGrainPatch call. Grain-density gain compensation (Sampler::m_grainGainComp, 1/sqrt(max(1, grainMs*0.001*grainRateHz))) is recomputed only when the blend changes (a knob turn), never per-note or per-active-voice-count, specifically to avoid the “dynamic 1/sqrt(activeVoices) pumps because it renormalizes against a count that changes on every note-on/off mid-sustain” anti-pattern already named for multitranspose’s own gain staging. Alternatives rejected: 6 raw sliders (incoherent at extremes, the original problem); a dynamic per-active-voice gain renormalization (would pump, same anti-pattern class as multitranspose’s rejected alternative). Revisit if: a 7th genuinely distinct grain character is needed — add a 7th named patch to the table rather than exposing a new raw parameter.

ADR-018 — Resonode voice-steal synthesizes a one-sample gate dip plus a frequency glide, rather than reassigning note/gate directly

Decision: allocateResonodeVoice’s steal path (reassigning a held voice’s fx/resonodevoice{v}/note to a new key while gate stays at 1.0 throughout) is paired with two Faust-side additions in resonode_synth.dsp: stealEvent/retriggerGate (a synthetic one-sample gate dip exactly on the steal instant, so pm.strike’s and the wash’s envelopes see a genuine rising edge and re-fire) and freqGlide (a one-pole glide to the new frequency over ~10ms on a steal, snapping instantly on a genuine fresh onset). Why: WITNESSED via the DawDreamer JIT harness that a steal with no correction produced two real defects: no fresh strike (both envelopes key off a literal gate rising edge, and a gate that never drops never re-fires either), and a real click (pm.modeFilter’s biquad coefficients jump in one sample under the frequency change, reusing stale internal state under abruptly different coefficients — measured derivative 0.057, over 2x a genuine fresh strike’s own onset derivative of 0.026). Evidence: with both fixes applied, the steal-instant peak derivative (0.34–0.41) matches a constructed reference of two legitimately overlapping strikes (0.34–0.63) rather than the pre-fix silent-pitch-jump artifact. Every idle/fresh-onset/sustain/release/4-simultaneous-voice scenario renders bit-exact (or within float32 rounding) against the pre-fix DSP — both additions are no-ops outside the steal case specifically. Alternatives rejected: forcing a real 0→1 gate edge from the control thread via a deadline-release mechanism (the “every momentary Faust gate must be explicitly released” pattern) — rejected as unnecessary complexity when the Faust-side synthetic-dip approach solves it with no cross-thread timing coordination needed. Revisit if: a future voice-stealing instrument needs the steal to sound like a genuinely distinct new attack rather than an overlapping-strike continuation — not the design intent here.

ADR-019 — Grid-beat visualization reads live DSP-derived beat index, never a separately-tracked UI counter

Decision: AudioThread::Telemetry::gridBeatIndex (0–15, or -1 with no master phrase established) is computed directly from masterPhaseSamples/masterLen — values the audio thread already tracks for loop quantization — and read by apc_leds.h’s rendering logic on the 4 dedicated top-right pads, wired through every midi.cpp refresh() call site. Why: matches the project’s existing “master phrase length comes from writeIdx telemetry, never wall-clock” discipline (see AGENTS.md’s Control Surface section) — a separately-tracked UI-side beat counter would drift from the real DSP-side phrase position under any tempo change or Link resync, the same class of bug that discipline already exists to prevent elsewhere. Evidence: verified via a standalone compiled+run C++ test covering all 16 beat indices plus the -1 (no master phrase) case, confirming correct cumulative fill (blank→yellow→red→green) behavior at each index. Alternatives rejected: a separate wall-clock-driven LED animation counter — rejected on the same grounds the master-phrase-length rule already rejects wall-clock-derived timing anywhere near the loop-quantization system. Revisit if: never — this is the same established pattern applied to a new UI surface, not a new tradeoff.

ADR-020 — effects_runtime.dsp’s REVAMT UI ceiling is 2.0, not the ported reverb.dsp’s own 1.0

Decision: effects_runtime.dsp’s REVAMT = hslider("REVAMT", 0.0, 0.0, 2.0, 0.001) exposes a 0–2.0 range to the control map even though effects/home/faust/reverb.dsp’s own verified/ported formula (reverb(amt,t,x) = x + revL*amt*0.25) is untouched. Why: direct user request for more reverb wet mix than the original hardware’s UI ceiling allowed. Widening the range at this runtime-control wrapper layer (not the hardware-parity-ported DSP itself) simply lets amt scale past 1.0 into the same linear formula — nothing about the verified math changes below REVAMT<=1.0, so hardware parity there is unaffected. Evidence: reverb.dsp’s formula is a plain multiply with no internal clamp, so doubling the exposed ceiling is a pure UI-range change, not a DSP change. Alternatives rejected: raising the ceiling inside reverb.dsp itself — rejected, that file’s contract is hardware-parity-verified and the extra range is a UI-only extension, not a hardware behavior. Revisit if: never — this is a settled UI range, not an open question.

ADR-021 — Home effects chain order is glitch(microrepeat) -> filter -> delay -> reverb

Decision: effects_runtime.dsp’s mainOut = preChain : microStage : filterStage : delayStage : reverbStage. Why: two direct user corrections, in order. Original (pre-session) order was pitch -> delay -> reverb -> micro -> filter. First correction moved filterStage before delayStage/reverbStage so that turning the filter shapes what feeds the reverb/delay tails, not just the dry/direct signal (order became pitch -> filter -> delay -> reverb -> micro). Second correction, from the user’s own words (“filter isnt applying to glitch, glitch should be before filter” and “glitch, once filtered, should feed into delay and reverb”), moved microStage before filterStage — glitch content must itself be filterable, which it was not when filter ran first. Evidence: both corrections came directly from the user after listening to the live device; no numeric measurement applies to chain ORDER (it is an audible mix-bus topology decision, not a parity/CPU question). Alternatives rejected: both earlier orderings (pitch->delay->reverb->micro->filter, and pitch->filter->delay->reverb->micro) — both superseded by direct user correction. Revisit if: a future effect stage is added and its natural position in the signal path is ambiguous — ask the user rather than guessing an order.

ADR-022 — Objekt renamed to Resonode; expanded to 6 modes/voice with real per-note velocity, patches re-swept on the new DSP

Decision: objekt_synth.dsp (and every “Objekt”-named C++/doc reference) is renamed to resonode_synth.dsp / “Resonode” — a name describing what it structurally is (a physical-modeling modal-resonator instrument), with no reference to Reason Studios’ commercial “Objekt” product anywhere in the tree. The DSP itself gained two real capabilities in the same pass: the mode bank grew from 4 to 6 modes per voice (mode5/mode6, same strength-reduced-pow()/alias-guard pattern as modes 2-4), and a genuine per-voice MIDI-velocity input (fx/resonodevoice{v}/vel, plumbed from onKeybedNoteOn’s existing vel parameter through dsp/aloop.dsp/effects_runtime.dsp) scales each voice’s exciter gain. The four named morphing patches (Percussive/MetalGlass/Strings/DanceBass) were RE-SWEPT from scratch against the new 6-mode DSP rather than assumed unchanged, since adding two modes measurably changes the acoustic result at any fixed (position,decay,damping,stretch) point — the re-sweep’s own empirical answer, not an assumption either way, is what settled it: the top pick for all four target directions landed on the EXACT SAME grid point as the original 4-mode sweep (kResonodePatches needed zero numeric changes), because all four target directions are dominated by pushing decay/damping/position/stretch to a grid extreme, and the two added lower-weighted modes shift absolute feature values without changing which corner wins. Why: the rename was requested directly (no product-name references, since this is an independent implementation, not a port of Reason’s proprietary DSP). The mode/velocity expansion was scoped by what genuinely improves performative closeness to a physical-modeling resonator instrument without abandoning the two already-settled hard constraints: mic-only excitation (no synthetic strike) and the Pi 4 CPU budget. A velocity-driven exciter-BRIGHTNESS coupling (multiplying the exciter’s pre-resonator lowpass cutoff by a per-voice velocity term) was implemented, measured, and then REJECTED before shipping: it defeated Faust’s cross-voice common-subexpression sharing of the lowpass coefficient computation (all 4 voices previously computed fi.lowpass(2, tone) against the IDENTICAL tone signal, letting the compiler share that coefficient computation once; giving each voice a unique tone*brightnessMul(velN) argument forced 4 independent coefficient computations instead of 1), nearly doubling total render cost for a change that measured as acoustically negligible (spectral centroid within 2% across vel 0.2/0.6/1.0, since the resonator bank’s own mode-frequency selectivity dominates timbre far more than the pre-filter cutoff — the same root cause already named in the tone-taper fix below). Velocity-driven GAIN (a plain multiply on the exciter’s envelope output, independent of any shared filter coefficient) was kept: cost-neutral and produced a real, large loudness range (rms 0.222/0.415/0.504 across vel 0.2/0.6/1.0). Evidence: DawDreamer JIT render-time A/B (12s render, x86_64, NOT faust2bench, NOT real Pi 4 hardware — a proxy only): old 4-mode/no-velocity median 0.153s; new 6-mode+velocity-gain-only median 0.286s (~1.86x); the rejected brightness-coupling variant measured 0.597s (~3.9x) for the same feature set, confirming the CSE-defeat hypothesis by isolating each contributing change independently (6-mode alone: ~1.98-2.15x; +velocity-gain-only: no further increase; +velocity-brightness-coupling: the extra ~2x on top). test/resonode-sweetspot/verify_musical_controls.py gained four new checks (velocity_response, silent_without_live_input, new_mode_alias_guard, voice_steal_with_velocity_change) alongside the three pre-existing ones (tone_taper, morph_glide_click, no_fadein_regression) — all seven pass against the shipped 6-mode+velocity-gain DSP. The patch re-sweep reused sweep.py’s existing 625-combo grid-search + select_patches.py’s empirical scoring methodology unchanged, adapted only for the renamed zones and the extra vel channel. Alternatives rejected: keeping the tone-brightness velocity coupling despite its cost (rejected — no CPU-optimization justification for a change whose own measured acoustic effect was negligible); increasing voice count (4->6) instead of/in addition to mode count (rejected — voice count multiplies the WHOLE per-voice cost including the exciter and envelope stages, not just the mode bank, and 4 voices already matches the keybed-driven steal-allocator’s established shape); assuming the old picks were still optimal without re-running the sweep, OR assuming they must have changed and hand-picking new values by ear/analogy (both rejected — the whole point of the empirical sweep methodology from the original patch selection is to not trust an assumption in EITHER direction about a parameter space that measurably changed; only re-running it settles the question). Revisit if: real Pi 4 faust2bench/on-hardware core_busy measurement (not available in this sandbox) shows the 6-mode expansion pushes Core 1 over budget — the next lever is dropping mode6 alone (the smallest-weighted, least structurally important addition) rather than reverting the whole expansion.

ADR-023 — LofiFx granulator latch flips on PRESS, not on release-if-quick-tap

Decision: ApcGrid::onLofiFxPress now toggles m_granulatorLatched (and applies it via setGranulatorEnabled) immediately on the press edge, unconditionally, every press. onLofiFxRelease no longer classifies press duration into “tap” (toggle) vs “hold” (no toggle) — it only handles the Resonode-disengage cleanup and bank revert. The 1-second Resonode-engage threshold in pollHolds is unchanged. docs/demo/faust-engine.js’s browser-demo mirror got the identical change for consistency. Why: requested directly — pressing the button should latch the granulator instantly rather than waiting to see whether the press turns into a quick tap or a hold. This also simplifies away the previous design’s “force-enable the granulator preview on every press regardless of latch state, then restore the latched state on release” workaround (see the pre-existing “LofiFx/granulator button” entry below, now updated in place) — that workaround existed specifically to make a tap’s eventual texture audible from the first sample even though the latch decision only happened at release; once the latch decision itself happens at press, the workaround is no longer needed. Evidence: reasoned through directly (this is a pure control-surface timing change, not a numeric DSP question) and cross-checked against every other consumer of m_granulatorLatched/granulatorHeld/resonodeEngaged state in the tree (apc_leds.h’s LED feedback block, docs/demo/faust-engine.js, docs/demo/index.html’s UI hint text) to confirm none of them assumed the old release-classified-toggle timing. Alternatives rejected: keeping the toggle at release but shortening kGranulatorTapMs (rejected — doesn’t address the actual ask, which is about press-vs-release timing, not tap-duration threshold); making every press force the latch ON rather than toggling it (rejected — a toggle preserves the ability to turn the granulator back off with a second press, matching the previous tap-to-toggle gesture’s actual capability, just moved earlier). Revisit if: real hardware testing shows a press that’s about to become a 1-second Resonode hold audibly and distractingly flips the background granulator on/off at the same instant — the lever then would be suppressing the toggle specifically on presses that go on to cross the Resonode threshold, at the cost of the latch decision no longer being knowable at press-time (it would have to wait to see whether the hold threshold is crossed).

ADR-024 — Dance Bass restored to kResonodePatches slot 3, replacing Wood/Membrane

Decision: slot 3 of Resonode’s 4 named patches goes back to being Dance Bass (position=0.42, decay=7.0, damping=0.15, stretch=-0.10, the original, already grid-search-verified point from before ADR-022) instead of the Wood/Membrane patch ADR-022’s follow-up commit put there. collision (which postdates the original Dance Bass sweep) is hand-set to 0.30 from a dedicated DawDreamer measurement, the same way the other three patches’ collision values were hand-set. select_patches.py’s TARGET_DIRECTION dict, docs/CONTROLS.md, docs/demo/index.html, and docs/demo/faust-engine.js’s mirrored RESONODE_PATCHES array all revert their naming/values to match. Why: requested directly (“we lost our dance bass, we must bring it back”) — Dance Bass was never deprecated by design, it was silently swapped out by a later commit whose own message (“Dance Bass -> Wood/Membrane”) frames it as a rename rather than the loss of a distinct, previously-shipped character. Both patches are legitimate points in the same 4-dimensional space, but the control surface only has 4 knob-blend slots, so keeping both simultaneously would need a 5th slot or a bank-switch gesture — out of scope for a restoration request. Slot 3 reverting to its pre-ADR-022-follow-up identity is the literal, minimal fix. Evidence: select_patches.py’s original DanceBass target direction (heavy lowFreqEnergyRatio bonus, strong negative spectralCentroidHz weight, stretchAbsPenalty favoring near-harmonic tuning) re-run against the current 6-mode+collision+pitch-mod engine via the existing sweep.py/select_patches.py 625-combo grid-search harness lands on the identical grid point used before ADR-022’s mode-bank expansion, for the same reason the other three patches’ picks carried over unchanged (the target direction is dominated by pushing decay/damping to their sustain-favoring grid extreme and stretch toward zero, which added modes/collision/pitch-mod don’t move). collision=0.30 comes from a same-environment DawDreamer JIT sweep at the shipped point (note 40, held, collision 0.0-0.6): decay-tail energy (first-diff-RMS proxy) rises monotonically 0.138->0.243 (+76%) while lowFreqEnergyRatio stays above 0.97 across the whole swept range, confirming the dominant sub-bass character survives a meaningful grit/drive boost. A new permanent dance_bass_shipped_patch check in verify_musical_controls.py renders the exact shipped point at notes 28/36/48 and asserts lowFreqEnergyRatio > 0.85, a sustain ratio (RMS at 500-600ms vs 50-150ms) > 0.5, and finite/bounded output — measured 0.94-0.97 and 0.86-0.94 respectively, well inside margin. Alternatives rejected: keeping Wood/Membrane and finding a 5th control surface slot (rejected — no free knob exists in the current LofiFx-bank layout; would need a new gesture, out of scope); keeping Wood/Membrane and discarding Dance Bass permanently (rejected — directly contradicts the request); re-deriving Dance Bass’s (position,decay,damping,stretch) from scratch instead of restoring the historical, already-verified point (rejected — the re-sweep confirms the historical point is still the empirical optimum for the same target direction, so re-deriving would just reproduce it at the cost of ~35 minutes of redundant DawDreamer renders). Revisit if: a future control-surface redesign adds a patch-bank-switch gesture (mirroring the LofiFx button’s existing dual-mode-via-hold-threshold pattern) — Wood/Membrane’s point (0.60, 1.20, 0.35, 0.05, collision 0.25) is still a legitimate, previously-verified character and could return as a 5th/6th named patch on a second bank rather than needing another sweep from scratch.
